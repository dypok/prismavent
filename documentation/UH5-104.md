# Development Summary – Delete Event

During the development of this user story, the complete event deletion functionality was implemented across both the Backend and Frontend, ensuring that the delete action is only available for events in the **"draft"** status, in accordance with the established business rules.

## Frontend

The **Delete Event** button was conditionally rendered on the event details page. The implementation uses the `status` returned by the **GET /events/{id}** endpoint to display the **Danger Zone** section only when the event is in the **"draft"** state, hiding it for all other statuses.

This approach provides a more intuitive user interface by preventing users from seeing actions that are not permitted based on the current state of the event.

## Backend

The **DELETE /events/{event_id}** endpoint was implemented with the necessary validations to ensure the integrity and security of the deletion process.

A validation function was added to verify that the event is in the **"draft"** status before allowing its deletion. If the event is in any other status, the system returns an **HTTP 400 Bad Request**, indicating that only draft events can be deleted.

Additionally, the endpoint verifies that the event belongs to the authenticated user. If the event does not exist or is not owned by the current user, it returns an **HTTP 404 Not Found**, preventing the exposure of metadata related to other users' resources.

Once all validations pass, the event is deleted along with its associated **event_items** and **guests** through database cascade deletion, returning a confirmation message to the client.

## Documentation and Testing

As part of the implementation, the integration documentation was updated by adding the section for the **DELETE /events/{event_id}** endpoint, including its behavior, business rules, expected responses, and possible error codes.

The testing documentation was also expanded by adding new test cases covering successful deletion scenarios, as well as cases where the event does not exist, does not belong to the authenticated user, or is not in the **"draft"** status.

## Result

This user story was successfully completed, ensuring that only the owners of events in the **"draft"** status can view and execute the delete action. The implementation enforces the business rules, protects user data, maintains a consistent user interface, and preserves data integrity through cascade deletion of all related records.

# Resumen de Desarrollo – Eliminar evento

Durante el desarrollo de esta historia de usuario se implementó la funcionalidad completa para la eliminación de eventos, abarcando tanto el Backend como el Frontend y asegurando que la acción solo esté disponible para eventos en estado **"borrador"**, de acuerdo con las reglas de negocio establecidas.

## Frontend

Se implementó el renderizado condicional del botón **Delete Event** dentro de la vista de detalle del evento. Para ello, se utilizó el estado (`status`) obtenido desde el endpoint **GET /events/{id}**, mostrando la sección **Danger Zone** únicamente cuando el evento se encuentra en estado **"borrador"** y ocultándola para el resto de estados.

Con esta implementación se garantiza una interfaz más intuitiva, evitando que el usuario visualice acciones que no están permitidas según el estado del evento.

## Backend

Se desarrolló el endpoint **DELETE /events/{event_id}**, incorporando las validaciones necesarias para garantizar la integridad y seguridad de la operación.

Se implementó una función de validación que verifica que el evento se encuentre en estado **"borrador"** antes de permitir su eliminación. En caso contrario, el sistema responde con un **HTTP 400 Bad Request**, informando que únicamente los eventos en estado borrador pueden eliminarse.

Adicionalmente, el endpoint valida que el evento pertenezca al usuario autenticado. Si el evento no existe o no pertenece al usuario, retorna un **HTTP 404 Not Found**, evitando la exposición de información sobre recursos de otros usuarios.

Cuando todas las validaciones son exitosas, el evento es eliminado junto con sus registros relacionados (**event_items** y **guests**) mediante eliminación en cascada en la base de datos, retornando un mensaje de confirmación al cliente.

## Documentación y Pruebas

Como parte de la entrega, se actualizó la documentación de integración agregando la sección correspondiente al endpoint **DELETE /events/{event_id}**, incluyendo su funcionamiento, reglas de negocio, respuestas esperadas y posibles códigos de error.

Asimismo, se amplió la documentación de pruebas incorporando nuevos casos de prueba que validan el comportamiento del endpoint en escenarios exitosos y en situaciones donde el evento no existe, no pertenece al usuario o no se encuentra en estado **"borrador"**.

## Resultado

La historia de usuario quedó implementada de forma integral, garantizando que únicamente los propietarios de un evento en estado **"borrador"** puedan visualizar y ejecutar la acción de eliminación. La solución asegura el cumplimiento de las reglas de negocio, protege la información de los usuarios, mantiene la consistencia de la interfaz y preserva la integridad de los datos mediante la eliminación en cascada de los registros asociados.
